3 · What would have been simpler as one agent with tools, and why?

All three of these tickets. The five-agent setup overcomplicated them, #101 most of all. Each one is a short chain of lookups plus at most one money request, and the MCP tools already enforce the important rules: amounts come from the database, a blocked vendor gets no PO, no negative cash, and humans approve. A single "desk agent" with the 16 agent tools could have:

  • #102 in one loop: get_ticket → get_lease_due → request_payment → set_ticket_status. In Run 1 the team called get_cash_position 4 times, list_approval_requests 4 times and get_lease_due twice for one $2,400 rent check. That's ~53k tokens across both runs, when the Boss-only close in Run 2 shows one agent can do a 102-sized job in ~11k.
  • #103: the margin math is deterministic (it's a tool). Accounting ran check_margin 3 times, and Customer Service then asked Accounting again to confirm $49.30 × 8 = $394.40, a number already in Accounting's ticket note. One agent would call check_margin once and write the draft itself.
  • The "closing" passes (102 run 2, 101 run 4) are pure status checks, ideal for one agent.

Why: every delegation costs a fresh context, so the delegated agent re-reads the ticket. On 101 Run 1, get_ticket was called 6 times (Boss 2, Inventory 2, Accounting 1, Customer Service 1), and nuance gets lost in each handoff message. The team's real benefits are least privilege (only Accounting can file a money request, only the Boss closes tickets), focused prompts, and readability for a human watching the floor. Those matter more as the board gets bigger and the work more varied. For three small tickets, one agent with the same MCP tools and the same human-approval gate would be cheaper, faster and just as safe. The team wasn't useless, though: having only Accounting file money requests is why every Cash tab row traces to exactly one request_payment / request_purchase_order by Accounting and one approval by Jane.

5 · Three new problems this team could not solve, and what it would need

💵 Selling things: revenue, fulfillment, refunds

Why not: nothing records a sale. Inventory never goes down when the AI Club buys 8 hoodies, cash never goes up, and refunds are impossible. In this homework, money only goes out. That's why every Cash tab row is negative and the AI Club's $394.40 offer on ticket 103 never shows up as cash.

Would need: MCP tools record_sale (inventory −qty, cash +revenue, a sales table), fulfill_order, and issue_refund (human-approved). A point-of-sale or payment-processor connector so revenue is real data, not typed in. A Sales / Fulfillment agent that turns an accepted quote into a fulfilled order, with Accounting reconciling deposits.

📦 Receiving deliveries as time passes

Why not: the tee is "arriving 2026-09-05", but desk.date_today never moves forward, and no tool adds received stock or closes a PO. Ticket 101 can only ever be "on order", never "handed to Tauhid". The Ticket 101 tab shows that exact limit: Run 3 stalled on "has it been ordered?", and Run 4 could only resolve it as on order with arrival 2026-09-05.

Would need: receive_purchase_order (inventory +qty, PO → received, check for short shipments), advance_shop_date / a scheduler that wakes the team when POs are due or rent is coming, and vendor tracking lookups. A Receiving agent (or an extended Inventory role) to check in shipments and then trigger Customer Service's "ready for pickup" draft.

✉️ Real conversations with customers and vendors

Why not: tickets only come from the seeded database, there's no create_ticket tool, drafts are never sent (by design), and nobody reads replies. If the AI Club answers "yes, send the 8" to draft #2 (Ticket 103 tab), the team will never know. Tauhid has four drafts (#1, #3, #4, #5) waiting for a human to send.

Would need: an email/inbox connector (MCP) that turns incoming mail into tickets with create_ticket, a send_message tool behind a human send-approval queue (like payments), and thread tracking that links replies to tickets. An Intake agent to classify and de-duplicate incoming requests and route them to the Boss, plus PII handling and rate limits in the safety layer.
